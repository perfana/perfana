Analysis Time Range — 3 Approaches

All share the same frontend dialog; differences are in API mutation strategy

A

Unified endpoint — recommended

New PUT /test-runs/:id/analysis-time-range accepts both offsets atomically. New column analysis_end_offset (stored as ramp_down DB column). UpdateAnalysisTimeRangeHandler writes both, triggers one stats-rollup job. The old /analysis-start-offset endpoint stays for backward-compat but is no longer wired to the UI.

Pros

  • Single atomic write — no partial state where start is saved but end isn't
  • One rollup re-trigger instead of two
  • Clean, discoverable contract

Cons

  • New endpoint to add (small lift)
B

Extend existing endpoint

Extend PUT /test-runs/:id/analysis-start-offset to also accept optional analysisEndOffset. Rename endpoint to /analysis-time-range (with a redirect from the old path). Single handler update.

Pros

  • Minimal new surface area
  • Fewer files to create

Cons

  • Muddies the existing handler's single-responsibility
  • Breaking change risk on old callers unless redirect added
C

Two separate endpoints

Keep existing PUT .../analysis-start-offset; add new PUT .../analysis-end-offset. Dialog saves both on confirm (two sequential requests).

Pros

  • Most surgical — each offset independently updatable

Cons

  • Non-atomic: if second request fails, state is inconsistent
  • Triggers rollup twice (double compute cost)
  • More API surface for same user action

Implementation note (shared across all approaches)

New property: analysisEndOffset = seconds from the end of the test to exclude (0 = no exclusion, same semantics as analysisStartOffset from the start). Stored in a new ramp_down DB column. Slider right handle position = duration − analysisEndOffset. Graph data served from a new lightweight GET /test-runs/:id/summary-timeseries endpoint querying the transactions + requests_error tables.
