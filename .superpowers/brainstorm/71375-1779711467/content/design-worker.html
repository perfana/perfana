Design — Section 2: Worker Changes

Every place analysisStartOffset is applied, analysisEndOffset is applied symmetrically

TransactionStatsRollupPipeline.ts

Before
const rampUpSeconds = testRun.analysisStartOffset ?? 0;
const cutoff = new Date(startTime + rampUpSeconds * 1000);

SQL: WHERE time >= $cutoff (ramp_up_excluded=true rows)
After
const rampUpSeconds = testRun.analysisStartOffset ?? 0;
const rampDownSeconds = testRun.analysisEndOffset ?? 0;
const startCutoff = new Date(startTime + rampUpSeconds * 1000);
const endCutoff = new Date(endTime − rampDownSeconds * 1000);

SQL: WHERE time >= $startCutoff AND time < $endCutoff (ramp_up_excluded=true rows)
// Full-run rows (ramp_up_excluded=false) remain unchanged — no cutoffs

metric-processor.ts (incremental JTL ingestion)

Change
// Currently marks ramp_up=true when elapsedSeconds < analysisStartOffset
// Add: also mark ramp_up=true when elapsed > (duration − analysisEndOffset)
const isExcluded = elapsedSeconds < startOffset
                 || (endOffset > 0 && elapsedSeconds > (duration − endOffset));

Same pattern applied in grafana-collector.ts and dynatrace-collector.ts wherever ramp_up is set.

MetricsPipeline.ts (Grafana time-range queries)

The Grafana query time range currently starts at startTime + analysisStartOffset. It will also end at endTime − analysisEndOffset (instead of always endTime). This clips the Grafana fetch window symmetrically.

DataSanityCheckPipeline.ts

Add a check: if the effective analysis window is zero or negative (analysisStartOffset + analysisEndOffset >= duration), add a dataWarning rather than marking the run invalid — the user deliberately set this, so it's a warning not an error.

Re-trigger on save

When UpdateAnalysisTimeRangeHandler saves both offsets, it enqueues a TransactionStatsRollupPipeline job — identical to what UpdateAnalysisStartOffsetHandler does today. One job, one rollup.
