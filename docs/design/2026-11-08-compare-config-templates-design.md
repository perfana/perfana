# Design: ADAPT compare-config templates in the UI, with a YAML round trip

Generated by /office-hours on 2026-11-08
Branch: claude/ds-compare-config-ui-management-d14681
Repo: perfana/perfana
Status: APPROVED
Mode: Builder

## Problem Statement

Golden-path ADAPT templates (`provisioned_template_ds_compare_configs`) can only be managed by
writing `template_ds_compare_configs.yaml` and restarting the API. There is no endpoint and no
UI. Perfana is installed on-prem and customers run everything themselves, so two groups are
stuck:

- **Customers with no provisioning directory** cannot manage templates at all.
- **Customers who keep provisioning in git** tune thresholds by hand in the anomaly card, then
  retype them into YAML. Even when they do, a template change never reaches a workload that has
  already completed a run, because `applyGoldenPathClassifications` skips every row it seeded
  before.

Goal: manage templates in the UI, and export them as valid provisioning YAML that is committed
back to the **same instance** through git, so that git becomes the source of truth and a change
in git changes behaviour.

## What Makes This Cool

The loop closes. Someone fixes the thresholds on a noisy panel in a real run's anomaly card and
clicks **Promote to template**. The template lands on a profile, and **Export YAML** produces the
drop-in file. They commit it, and on the next restart the row comes back provisioned and
read-only. On the next completed run of every matching workload, the template re-applies to the
rows it owns and leaves hand edits alone. One person tunes, git keeps the record, and nobody
types a threshold twice.

## Constraints

- On-prem, customer-operated. The export goes back into the same instance's provisioning
  directory, so it has to be byte-stable: export, re-provision, export again must produce no
  diff.
- Provisioning code is the single schema. `ProvisioningService` and `MetricClassificationYaml`
  (`apps/api/src/modules/provisioning/provisioning.service.ts`) define the format, and the
  exporter may not hand-maintain a second one.
- The install has exactly **one** template file. `loadYamlFile(dir,
  'template_ds_compare_configs.yaml')` is the only reader.
- The template table has **two writers today.** Provisioning writes templates
  (`system_under_test_id IS NULL`). `classifyMetric`, behind `POST
  /test-runs/:testRunId/classify-metric`, writes **system-scoped** rows into the same table, and
  nothing in `apps/web` calls it. Every path in this design is scoped to
  `system_under_test_id IS NULL` and leaves those rows alone.
- **The template table has no row-level security** (`rls: false` in the RLS policy snapshot).
  The service-layer organization filter is the only boundary on it, and `withRequestEm()` adds
  no filtering there.
- `ds_compare_config` carries `trigger_mark_stale_on_config_update`, which marks a workload's
  ADAPT results stale whenever `config_data` changes at all. Anything written into `config_data`
  that is not effective configuration would mark results stale for nothing.
- Migrations numbered above 1791 may not use `SAVEPOINT` and may not rely on the batch to roll
  back for them (root CLAUDE.md #64). The template table is small and is not a hypertable, so a
  plain `ALTER` is fine.
- NULLs never collide in a btree unique index (the `uq_benchmarks_unique` lesson, api CLAUDE.md
  "Two SLOs on one panel"), so every nullable key column is wrapped in `COALESCE`.

## Premises

1. **Two objects, two steps.** Hand tuning happens on `ds_compare_config`: one workload's panel,
   keyed on this deploy's `application_dashboard_id` uuid. Getting that tuning into YAML means
   promoting a tuned row into a template (uuid → dashboard uid + panel id or title), then
   exporting templates. Exporting raw `ds_compare_config` rows is useless for provisioning.
2. **One schema, both directions.** The template YAML grows to cover everything the UI edits.
   The exporter is built from the reader's own type and module, and a round-trip spec guards it.
   The applier needs a decided precedence for those fields, not just a bigger YAML (§2).
3. **Git owns what git declares.** The install's one template file is the declared state of every
   provisioned template. Provisioned rows are read-only in the UI. Provisioning a key that a UI
   row already holds takes that row over: this is the round trip. A provisioned row whose key is
   no longer in the file is deleted on the next boot, but only when the file exists and parses. A
   missing or broken file means "no opinion".
4. **A template belongs to a profile, an organization, or the install.** A profile template
   applies only to runs whose tags match the profile, inside its organization. An organization
   template applies to every run in that organization. An install-wide template
   (`organization_id IS NULL`) applies to every run, and is what an existing YAML without
   `organizationId` produces, so existing files keep working.
5. **Template-owned rows follow the winning template** (revised after the second opinion). On each
   completed run, every row the golden path owns (`updated_by = 'system:golden-path'`) is rebuilt
   from its base config plus the fields of whichever template currently wins for it by precedence
   (§2). It writes only when the result differs. A row a person saved is never touched. If no
   template matches the row any more, it is rebuilt from its base, so deleting a template behaves
   exactly like removing all its fields.

## Cross-Model Perspective

A cold-read Claude subagent (Codex is not installed) reviewed the premises:

- **Critical, accepted:** premises 3 and 5 as first written contradicted each other. A row
  stamped `GOLDEN_PATH_ACTOR` counts as existing and is skipped forever, so a GitOps change would
  be a no-op on every workload that had run once. This is now premise 5.
- **High, accepted:** a bigger YAML changes nothing on its own. The insert branch hardcodes
  `percentageThreshold: 0.15`, `iqrThreshold: 2`, `aggregation: 'mean'`, and the merge branch
  keeps the worker's values. The applier needs a precedence rule.
- **High, accepted:** the provisioning upsert key lacks `metric_name` and the organization, so
  adding either would make entries overwrite each other.
- **Medium, accepted:** templates already seed across organizations. The applier reads them with
  no organization filter, and `handleCompletedTest` passes neither tags nor an organization.
- **Rejected:** "leave profiles out until the key is fixed." The key fix comes first (PR 1) and
  the profile column follows in PR 2, and profiles are the cheapest organization scoping
  available.
- **Its coolest idea, kept as a follow-up:** backtest a template change against the workload's
  stored statistics before committing it, and mine hand edits for promotion suggestions ("raised
  by hand in 7 of 9 workloads").

## Approaches Considered

- **A: Org-wide Settings page.** Not chosen: it builds a second table and dialog beside a profile
  page that already has both, and it cannot give JVM and .NET services different template sets.
- **B: Templates as a profile tab.** Chosen.
- **C: Export the live per-workload config, no editor.** Not chosen: customers without a
  provisioning directory still could not manage templates.

## Recommended Approach

Approach B, in three PRs. PR 1 is the backbone and ships value alone: git changes reach running
workloads. PR 2 adds profiles. PR 3 adds Promote.

### 1. Data model

**PR 1 migration**

Statement order is fixed, and pinned in a spec the way 1799's shape is pinned. The **first**
statement of `up()` is the duplicate check below, before any DDL on either table. Every later
statement is idempotent (`ADD COLUMN IF NOT EXISTS`, `CREATE UNIQUE INDEX IF NOT EXISTS`, and
backfills that are safe to repeat). Above 1791 the batch may have no transaction to roll back,
so a migration that fails partway has to be safe to simply re-run once the operator has fixed
the data.

- `provisioned_template_ds_compare_configs.read_only boolean NOT NULL DEFAULT false`. Backfill
  `true` where `created_by = 'system:provisioning'` and `system_under_test_id IS NULL`.
- A **partial** unique index `WHERE system_under_test_id IS NULL` on:

  ```
  COALESCE(organization_id::text, 'install'),
  COALESCE(dashboard_uid, ''),
  regex,
  COALESCE(panel_id::text, 'title:' || panel_title),
  COALESCE(metric_name, '')
  ```

  - The panel title is part of the identity **only when there is no panel id**. Beside a panel id
    it is a descriptive attribute that can be edited without changing which template the row is.
  - The `system_under_test_id` rows written by `classifyMetric` are outside the index and outside
    every path below. Retiring `classify-metric` is a separate cleanup.
  - The duplicate check (the first statement, see above) counts duplicates under this key. When
    there are any, it throws an error that lists each duplicate group's ids and says to delete
    all but one of each, then re-run. Provisioning itself cannot have created duplicates under
    this key, since every column of the old upsert lookup is in it. Duplicates come from two API
    replicas booting together and racing the unguarded find-then-insert, and from the old
    `findOne`, which did not filter on `system_under_test_id`.
- `provisioned_template_ds_compare_configs.config_overrides` gains `higherIsBetter` with presence
  semantics (§3). It is backfilled from the `higher_is_better` column where that column is not
  NULL. A NULL column on a legacy row reads as "not named".
- `ds_compare_config.template_id uuid NULL`: which template last applied to the row. It is a
  **plain uuid with no foreign key**, because it is display provenance only and never gates
  ownership. A dangling id renders as "template removed". With no FK, the SUT export and import
  carry the column as ordinary data. The referenced templates are never exported, because they
  are live configuration and would start seeding runs in the target environment. A sut-transfer
  spec case covers a row with `template_id` set.
- `ds_compare_config.template_base jsonb NULL`: the row's configuration before any template
  applied (§2). Both columns sit outside `config_data`, so writing them never fires the stale
  trigger.

**PR 2 migration**

- `provisioned_template_ds_compare_configs.profile_id uuid NULL REFERENCES profiles(id) ON DELETE
  CASCADE`.
- Replace the scope term in the unique index with
  `CASE WHEN profile_id IS NOT NULL THEN 'profile:' || profile_id
  ELSE 'org:' || COALESCE(organization_id::text, 'install') END`.
- A profile template's organization is its profile's. `organization_id` on a profile template is
  set from the profile on write and is not part of its key.

The table keeps its name. `provisioned_` becomes a misnomer once the UI writes rows, but a rename
touches the entity, the RLS snapshot, the SUT transfer graph and the ConsolidatedSchema for no
behaviour gain.

### 2. Applier (`applyGoldenPathClassifications`)

**Inputs.** Add `organizationId` (PR 1) and `tags` (PR 2) from the `TestRun` that
`handleCompletedTest` already holds.

**Selection.** Templates with `system_under_test_id IS NULL` and
`(organization_id IS NULL OR organization_id = run.organizationId)`. In PR 2, also
`(profile_id IS NULL OR profile_id IN <profiles matching the run>)`. Profile matching uses one
helper in `packages/shared`, extracted from
`apps/grafana-sync/src/modules/auto-config/auto-config.service.ts:122`, and it **fails closed**:

- A run with no organization matches no profile and no organization template, only install-wide
  ones.
- A profile with no organization never matches.

grafana-sync switches to the same helper. `test_runs.organization_id` is NOT NULL in the DDL, so
removing its fail-open arm changes nothing on a real run, and the helper's spec pins the
cross-organization case.

**Precedence**, a total order from most to least specific:

1. Dashboard match: exact uid > regex uid > wildcard (no uid).
2. Scope: profile > organization > install-wide.
3. Panel match: panel id > literal panel title > regex panel title.
4. Profile name, ascending, between two profiles.
5. Template id.

Step 5 is reachable: two templates in the same scope with overlapping regexes (`^jvm-.*` and
`^jvm-prod.*` both match `jvm-prod-1`) have different keys and tie through step 4. Uuid order
decides them, which is stable but arbitrary. So any tie that reaches step 4 or 5 is recorded once
in the run's summary line, naming both templates, never once per panel. The applier spec pins one
case per adjacent pair of steps, including two overlapping regex templates.

**Ownership**

- `updated_by = 'system:golden-path'` means the row is template-owned. It is rebuilt on every
  completion from `template_base` plus the fields the **current winner** names.
  - A newly added, higher-precedence template therefore takes over rows a lower one seeded.
  - A removed template hands its rows to the next template that still matches them.
  - With no match left, the row is rebuilt from `template_base` alone and `template_id` is
    cleared. Deleting a template therefore strips its fields from every row it owned. What is
    left is each row's own base, which depends on how the row was born (insert defaults, the
    worker's or Dynatrace's seeded config, or a pre-upgrade row's config with the old template
    values still in it). A workload created after the delete gets no golden-path row at all.
  - **Collection-gap guard, per row.** Title templates resolve against the panel list the applier
    already reads: the distinct `ds_panels` rows recorded for the dashboard by the system's 10
    most recent **completed** runs. These are earlier runs whose panels were written during their
    own analysis, so the list does not depend on the completing run's panels existing yet. When a
    template-owned row's own panel id is missing from that list, title ownership for that row
    cannot be decided, so the row is left untouched. A dashboard with no recorded panels leaves
    all its rows untouched. A panel missing from collection therefore never makes that row's config
    flap from one run to the next. An applier spec case covers a non-empty list that lacks one
    row's panel.
- `updated_by = 'worker-pipeline'`, or a NULL author with `source = 'dynatrace-host'`, is
  machine-seeded. On its first merge, `template_base` is set to the row's current `config_data`,
  and from then on the row is template-owned.
- Any other `updated_by` is a hand edit and is skipped.
- The metric-level / panel-level distinction for "already configured" (v0.2.97.44) is unchanged.

**Field precedence.** Effective config = `template_base` ⊕ the winning template's named fields.
A field is "named" when its key is present in the template's `config_overrides`, explicit `null`
included. `metricClassification` is required in YAML, so it is always named. `higherIsBetter` is
named only through `config_overrides`: a template without it leaves the row's value alone, and an
applier spec case pins exactly that. Legacy templates wrote `higherIsBetter: null` whenever the
YAML omitted it. Under this rule they leave the base value instead. For an inserted row that is
the same `null` default. For a **machine-seeded** row (worker-pipeline, or untouched dynatrace-host)
merged for the first time after the upgrade, it is a behaviour change: today the merge nulls the
row's direction, and after the upgrade the row keeps the direction the worker or the Dynatrace
path set. A row with a direction can fail a run on a regression, and a null-direction row never
can (root CLAUDE.md #63). Pre-upgrade golden-path rows do not change, because their base already
holds the null. The CHANGELOG callout tells customers that a template relying on an omitted
`higherIsBetter` must now say `higherIsBetter: null` explicitly to keep today's behaviour, and the
Assignment counts how many templates that affects.

- A row the applier inserts gets the existing insert defaults as its `template_base`.
- Because the base is stored, a field the template stops naming **reverts** to the base on the
  next re-merge. For the fields the template names, git stays the truth: two workloads under the
  same template converge on them whatever their history. Fields it does not name come from each
  row's base, so they converge only where the bases agree.
- A golden-path row written before the upgrade has no `template_base`. Its first re-merge takes
  its current `config_data` as the base, but only when the winner would not change it. Before
  v0.2.95.42 a hand edit kept `updated_by = 'system:golden-path'`, so a legacy row the winner would
  change may hold a user's edit and is left alone (correction from the /ship adversarial review,
  2026-11-08). Documented in the CHANGELOG.

**Write only on a difference.** Compare the rebuilt `config_data` with the stored one and update
`config_data` only when they differ. Separately, write `template_id` whenever the winning
template's id differs from the stored one, clearing it included, even when `config_data` is
unchanged. The column sits outside `config_data`, so that write never fires the stale trigger,
and the UI never names a template that no longer applies to the row. Two applier spec cases
cover it: a winner change with an identical config, and an unmatched row whose config is
unchanged. Because provenance lives in columns, the stale
trigger fires exactly when effective configuration changed. After the upgrade, the first completed
run marks earlier ADAPT results stale only on workloads whose effective config the re-merge
actually changed, and the CHANGELOG says so.

**Ordering, verified.** `handleCompletedTest` awaits the applier and only then enqueues ADAPT
(`test-runs-mutation.service.ts:418-441`), so the completing run is the first one judged on the
re-merged config. The collection-gap guard reads the panels of the system's 10 most recent
completed runs, which the completing run may or may not already be among.

### 3. Provisioning (`provisionMetricClassifications`)

**YAML fields added**

- PR 1: per-item `organizationId`, overriding the file-level one, plus `metricName`,
  `percentageThreshold`, `iqrThreshold`, `aggregation`, `minSampleCount` and
  `defaultValueIfControlGroupMissing`. These and `higherIsBetter` go into `config_overrides`
  (jsonb), present only when the item names them, explicit `null` included. The
  `higher_is_better` column is kept in sync for display and audit, but presence is read from
  `config_overrides` only. A YAML `higherIsBetter: null` therefore round-trips as an explicit
  null, which is how a template forces the informational value the Dynatrace path writes on
  purpose (root CLAUDE.md #63 explains why that value changes verdicts).
- PR 2: `profile`, resolved by name like `profile_benchmarks.yaml`.
  - An unknown profile skips the item with a warning, and the item's key still counts as declared,
    so it is not pruned.
  - A profile item whose `organizationId` differs from its profile's is skipped the same way.

**Key.** The unique index above. Every lookup filters `system_under_test_id IS NULL`, which also
fixes today's `findOne`, which does not.

**Counts.** Report `created`, `updated`, `unchanged`, `takenOver` and `pruned` separately.
`unchanged` needs a compare before writing; today every boot reports every item as updated.

**Takeover.** A file key held by a UI row (`read_only = false`) sets `read_only = true` and
`updated_by = 'system:provisioning'`. It counts as `takenOver`, never as `updated`.

**Prune**

- Collect the declared keys from the parsed items **before** any write, so an item that fails to
  write is still declared.
- Then delete every `read_only = true` row with `system_under_test_id IS NULL` whose key was not
  declared. One file per install means one prune scope.
- Prune only when the file exists and parses. An explicit `items: []` prunes every provisioned
  template, because it is a declared empty state.
- Log each pruned row.

**Adding `organizationId` to a legacy file.** Its keys change: the next boot creates
organization-scoped templates and prunes the install-wide ones. Template-owned rows in that
organization follow the new winner, which matches the same panels. A row with no match left is
rebuilt from its base and its `template_id` is cleared. On an install with more than one
organization, that applies to every template-owned row in the **other** organizations: on their
next completed run they lose the template's fields, except pre-upgrade rows whose base already
holds them. This consequence goes in the CHANGELOG callout, and an applier spec case covers it.

### 4. Export

**Endpoint and output.** `GET /provisioning/compare-templates/export` returns the install's
**whole** `template_ds_compare_configs.yaml`: every template with
`system_under_test_id IS NULL`, provisioned or UI-created, across all scopes. It is a drop-in
replacement for the one file the install reads. Only a global admin may call it, because the
file is install infrastructure and declares every organization's provisioned templates.

**Why the whole file.** With prune, the file is the complete declared state. A partial file
committed in place would prune every template it left out.

**Organization in the file.** When every item shares one organization (install-wide included),
the file carries a file-level `organizationId` and the items carry none. Otherwise items carry
their own `organizationId` and the file-level one is omitted.

**Built from the reader's own types.** Row → `MetricClassificationYaml` lives in the same module
as the reader.

**Field presence.** Export a key exactly when it is present on the row:

- a set identity column: `dashboardUid`, `panelId`, `panelTitle`, `metricName`;
- `regex`, written only when true. A hand-written `regex: false` is dropped on the first export;
- the descriptive `dashboardLabel` when set (it is not part of the key);
- the required `metricClassification`;
- a key present in `config_overrides`, explicit defaults and explicit `null` included.
  `higherIsBetter` is read from `config_overrides`, never from its column.

Never omit a key because its value equals a default, since presence is what makes a template
force a value. The canonical round-trip input includes an item with a `regex: true`
`dashboardUid` and an item with a regex `panelTitle`.

**Deterministic order**, a total order over the key:

1. Scope: install-wide, then organizations by id, then (PR 2) profiles by name.
2. `dashboardUid`: absent first, then ascending.
3. `regex`: false first.
4. Panel: id items (ascending) before title items (ascending).
5. `metricName`: absent first, then ascending.

Keys inside an item are written in a fixed order.

The first export of a hand-written file drops its comments and reorders its keys, so the file is
byte-stable from the second export on. The Export YAML copy in PR 2 says so.

**Round-trip spec**

- YAML → provision → export is byte-identical to the canonical input.
- A second provision reports 0 created, 0 updated, 0 taken over, 0 pruned.
- A UI-created row is taken over with identical content.
- Cases for an explicit default, an explicit `null`, rows that tie on all but one key column,
  and a legacy file gaining `organizationId`.
- Mutation-check it by dropping one field from the exporter and confirming the spec fails.

### 5. API and UI

**Routes**

- `GET/POST/PUT/DELETE /profiles/:id/compare-templates` (PR 2), mirroring
  `/profiles/:id/benchmarks`.
- `GET/POST/PUT/DELETE /compare-templates?organizationId=…` for organization templates (PR 1 API,
  PR 2 UI).
- `/compare-templates?scope=install` for install-wide ones.

**Read access**

- Profile and organization templates: members of that organization, with the same rule as
  `GET /profiles/:id/benchmarks`.
- Install-wide templates: any authenticated user, because they apply to everyone's runs.
- A caller-named `organizationId` is checked for membership in the service. RLS does not backstop
  it, and this table has none. A resource outside the caller's organizations answers **404**,
  not 403.

**Write access**

- `benchmark:manage` in the template's organization. Install-wide templates need a global admin.
- Read-only rows refuse `PUT`/`DELETE` with 409.
- Create, update and Promote map a unique violation on the new index (23505) to a **409 naming
  the conflicting scope and key**. This follows "Turning a constraint violation into a 409" in
  `apps/api/CODING_RULES.md`: the controller lets `HttpException` through, and a SAVEPOINT guards
  any place inside the RLS request transaction that swallows the error.
- Writes are audit-logged.

**UI**

- A fourth tab, "ADAPT templates", on `/settings/profiles/[id]`, beside Dashboards, Service Level
  Objectives and Deep Links.
- A table plus an edit dialog that reuses the anomaly card's `MetricConfigForm`.
- The profiles list gets two pinned entries that open the same tab without a profile:
  - "All runs in <organization>", for organization templates, shown to members.
  - "All runs on this install", for install-wide templates, editable only by global admins.
  - A scope badge tells the three kinds apart everywhere they are listed.
- Read-only rows show a lock. "Copy to editable" asks for a **different** scope, another profile
  or organization, because a copy in the same scope has the same key as the provisioned row. To
  change a provisioned template in place, you edit the YAML.
- The dialog states the reach: "Applies on the next completed run of matching workloads to panels
  nobody has hand-edited."
- **Export YAML** sits on the install-wide entry, visible to global admins.

### 6. Promote (anomaly card, PR 3)

- **Action:** the row settings form gets **Save as template**. It resolves the row's
  `application_dashboard_id` to `dashboard_uid`, takes the panel id and title, and takes the
  metric when the scope is metric.
- **Targets:** profiles matching this run, "All runs in <the run's organization>", and, for global
  admins, "All runs on this install".
- **The current row** stays a hand edit, so promotion never changes the workload it came from.
- **Generalising the dashboard:** the form offers "this dashboard" (exact uid) or "every dashboard
  with this panel title" (panel title, no uid). A Dynatrace host or perf-test scenario dashboard
  has a uid per host or per scenario, where an exact uid is almost never what the user means.

## Implementation deviations (PR 1, recorded at /ship, 2026-11-08)

PR 1 as built differs from the body above in five places, beyond the amendments the Eng Review below
already records (D7 and D8 move the `/compare-templates` CRUD API and the export route to PR 2; D10
reads the organization from each application dashboard instead of the `TestRun`). The body stays as
the plan of record; the code, `apps/api/CLAUDE.md` and
`docs/reference/Features/Compare Config Templates.md` describe what shipped.

1. **`read_only` is nullable** with `DEFAULT false`, not `NOT NULL` (§1). A SUT import inserts through
   `json_populate_recordset`, which yields NULL for a key an older bundle lacks, so `NOT NULL` would
   fail every pre-1822 bundle. Readers treat NULL as false.
2. **The collection-gap guard covers title-owned rows only** (§2). A dashboard with no recorded panels
   does not freeze every row on it: perf-test dashboards never get `ds_panels` rows, so an id-owned row
   is rebuilt regardless. A row with no `template_id` (pre-1822) waits only when no template wins it and
   a title template of its metric reaches the dashboard.
3. **`higherIsBetter` falls back to the `higher_is_better` column** when the override key is absent
   (§3, §4). An API older than 1822 rewrites `config_overrides` without the key and keeps the column,
   and the applier and the exporter both read the column then. `apps/api/CLAUDE.md` rule 5 explains why
   the fallback stays.
4. **The provisioning lock is polled, not blocking** (correction C1). `pg_try_advisory_lock` is retried
   30 times at 1 s; a replica that cannot get it skips template provisioning for that boot with an
   error instead of hanging startup behind a holder whose host died.
5. **One failure suppresses the whole prune** (§3 Prune). Any item whose identity cannot be read, or
   any template that failed to write, means nothing is pruned that boot, so a typo cannot delete the
   templates it was meant to replace.

Two more came out of the /ship adversarial review. The first is corrected in the body: a pre-1822
golden-path row is adopted only when its winner would not change it (§2, Field precedence). The second
is recorded only here: every applier write is conditional on the author it read, so a save that lands
while the applier runs wins and the row is skipped that time (`apps/api/CLAUDE.md` rule 8).

## Implementation deviations (PR 2, 2026-11-08)

from the body in these places; the code, `apps/api/CLAUDE.md` and

## Success Criteria

- A customer with no provisioning directory creates, edits and deletes a template, and it seeds a
  new workload's panels on that workload's next completed run.
- Changing a template's `absThreshold`, in the UI or in YAML, changes the template-owned row of an
  existing workload on its next completed run, and leaves a hand-edited row on the same panel
  untouched. Removing a field from the template reverts that field to the row's base.
- Export, commit, restart: provisioning reports only `takenOver` for the UI-created rows, and the
  rows show read-only. A second restart reports 0 created, 0 updated, 0 taken over, 0 pruned.
- Deleting an entry from the YAML removes the template on the next boot. Its rows go to the next
  matching template, or are rebuilt from their base when none matches.
- A template in organization A never seeds organization B's runs.
- The round-trip spec passes, and fails when a field is dropped from the exporter.

### Unresolved at the cap

1. R3-1 — consistency (blocking): This round replaced the 'keeps its last applied values' rule in premise 5, §2 Ownership and the success criteria, but §3 'Adding organizationId to a legacy file' still states the old rule: 'No workload loses its config' and 'a row with no match keeps its values'. Under the new rule a row with no match is rebuilt from template_base and its template_id is cleared. On an install with more than one organization, adding organizationId narrows a template to one organization, so the rows it owns in every other organization have no match left. Each of them is rebuilt from its base on its next completed run. Rows inserted after the upgrade, whose base is the insert defaults, lose the template's values. Pre-upgrade rows keep them, because their base was taken from a config_data that already held those values. An implementer following §3 would build the rule this round dropped.
2. R3-2 — consistency (blocking): The new Ownership bullet says that with no match left 'template_id is cleared'. 'Write only on a difference' says the applier updates 'only when they differ', meaning when the rebuilt config_data differs from the stored one. The two rules conflict whenever the rebuilt config equals the stored one, and on an existing install that is the usual case. A pre-upgrade row's base is its config_data at the first re-merge, template values included, so removing its template changes nothing in config_data and template_id is never cleared. The case R2-8 raised is also still open: when another template starts winning with an identical effective config, template_id keeps naming the old one. When a template is narrowed or moved to another organization rather than deleted, the UI keeps naming a live template that no longer applies to the row.
3. R3-3 — completeness (blocking): Rebuilding an unmatched row from its base, the rule this round adopted, makes a missed title match costly. Each flip rewrites config_data, and the stale trigger marks ADAPT results stale. The collection-gap guard covers one case only: a dashboard whose ds_panels list is empty. When the list is not empty but lacks one panel, the title templates cannot match that panel's row. The row is rebuilt from a lower template or from its base, and flips back on the next run in which the panel is present. So the claim 'A gap in panel collection never makes config flap' does not hold for a partial gap. The design also does not say which ds_panels rows count as 'this run' (rows keyed to the completing run, or the dashboard's latest), nor whether they are written by the time handleCompletedTest calls the applier. If the worker's analysis writes them afterwards, the list could be empty on every completion and the guard would freeze every template-owned row.
4. R3-4 — consistency (blocking): §2 now reads a legacy NULL higher_is_better as 'not named', and claims only that for an inserted row the result is 'the same null default'. It says nothing about machine-seeded rows, and those change. Today the merge writes the template's higher_is_better onto a worker-pipeline or dynatrace-host row (apps/api/CLAUDE.md: 'higher_is_better comes from the template'), so a template that omitted the field nulls the row's direction. With a null direction a regression can never fail a run (root CLAUDE.md #63). Neither the Distribution Plan's CHANGELOG callout nor the Assignment mentions this.
