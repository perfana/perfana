# Design: Test-run comments, threads and numbered graph markers

Generated by /office-hours on 2026-11-19
Branch: fix/splunk-epoch-time (design only; implementation goes on its own branch off origin/main)
Repo: perfana/perfana
Status: APPROVED
Mode: Builder

## Problem Statement

Performance engineers review a finished test run with their team the morning after. Today that discussion happens outside Perfana (chat, screenshots, the meeting itself), so it is lost from the run, cannot point at a moment on a chart, and never reaches the report. Users need to comment on any card of the test-run details page, reply in threads, see what is unread, get notified in their team channel with a deep link, place numbered markers on a graph and discuss each one, and optionally include all of this in a report. Every comment carries its author and a timestamp.

## What Makes This Cool

- A numbered marker is not a sticky note. It is pinned to a moment of the run and stores the chart its author was looking at, so anyone opening ② (from the drawer, a Slack link or the report) sees the same series over the same time range.
- Marker and comment are one object: a marker is a comment with a time anchor. One table, one thread model.
- The analysis done in the UI becomes the report narrative, instead of being retyped.

## Constraints

- Multi-tenant RBAC: every new table carries `organizationId` / `teamId` inherited from the test run (camelCase in `repo.create`, CLAUDE.md "Resource creation"), RLS policies, and service-layer org checks on every route, including by-id reads (CLAUDE.md Common Issue #48: 404 not 403 outside the caller's orgs).
- Realtime goes through `TestRunsGateway`, with ownership carried on the event payload, never a broadcast (Common Issue #58).
- Repo is public: no real customer names in fixtures or docs.
- No email delivery exists in Perfana; external notification is the per-SUT `notification_channels` webhooks only.
- Stored report HTML is never regenerated; comments appear only in reports generated after the feature ships.

## Premises (all agreed)

1. Comments live in a new run-scoped table `test_run_comments`, not in `events`. `events` stays SUT/environment/workload-scoped and Grafana-synced; its overlay rendering in `GraphsChart.tsx` is reused, its table is not.
2. **(Revised after second opinion.)** A marker is a root comment on the Graphs card with `marker_time`, a `chart_context` jsonb (the card's existing `MetricSeriesRef[]` link format, x-range, optional graph preset id) and a stable per-run `marker_seq` that is never reused. The deep link and the report both draw from `chart_context`. v1 shows markers on the Graphs card only.
3. Threads are one level deep: a root plus a flat list of replies.
4. Unread is a per-user `last_seen_at` per test run and card (revised in the data model: reads are per card). The badge counts comments newer than it by other authors, shown on each card header, the run header and the test-run list. No per-comment read receipts, no inbox.
5. External notification reuses `notification_channels` with a new `notify_on_comment` flag (default off), posting to the team channel with a deep link, batched per run over a ~2 minute window. No per-user email, no @mentions in v1.
6. Deep link: `/test-runs/:id?card=<key>&comment=<id>` expands the card, replays the marker's `chart_context` through a new `GraphsViewRequest` on `CardLinkRequestContext` (see Marker view replay; the existing single-series link cannot carry it), opens the drawer and highlights the thread.
7. Reports get an option to include comments, with markers drawn as numbered callouts on a chart built from `chart_context`.
8. Anyone who can view the run can comment; only the author edits; author or org admin deletes; edits show "(edited)".

## Cross-Model Perspective

- **Coolest unconsidered version:** save the chart view on every marker, then use it for cross-run memory: when ADAPT regresses on the same metric in a later run, surface the earlier run's thread ("last time this spiked, it was GC, fixed by a heap bump").
- **What it read as the core:** "performance engineers analysing a run with their team the morning after", so markers, threads and live updates come first; webhooks and reports are support.
- **Existing tools:** Grafana annotations cover time-anchored text and rendering but not threads, unread state, run scope or RLS. Liveblocks/Velt cover the comment UX but are SaaS, so tenant data would leave Postgres; study their UX, do not adopt.
- **Challenged premise (High), accepted:** a marker with only `marker_time` + one series key points at nothing for a second user, because the Graphs card's series live in client state and `revealCard` (`apps/web/app/test-runs/[id]/page.tsx:222`) only expands the card. Verified in code. Fixed by premise 2's `chart_context`, replayed through a new `GraphsViewRequest` on the same context (`page.tsx:298`) that "Open in Graphs" uses; the existing single-series request cannot carry it. It also asked for stable marker numbering, adopted as `marker_seq`.

## Approaches Considered

### Approach A: Threads first
Card-level threads, unread badges, live updates and deep links only; markers, webhook and reports later. Not chosen: it leaves out the graph-marker interaction and the report option the spec asks for. It survives as PR1 of B.

### Approach B: Full feature on one model, 3 PRs (chosen)
Schema decided once up front, delivered as three independently shippable PRs.

### Approach C: Comments as a platform primitive
Polymorphic anchor over runs, SLOs, ADAPT results, reports. Rejected: builds for resources nobody asked to comment on, and loses `ON DELETE CASCADE` and plain RLS inheritance from the run.

## Recommended Approach

Approach B.

Wireframe: projects/perfana-perfana/daniel-fix-splunk-epoch-time-sketch-20261119-204003.png (drawer per card; card threads and marker threads in one list; "restore view" replays `chart_context`).

### Data model

`test_run_comments`
| column | type | note |
|---|---|---|
| id | uuid PK | |
| test_run_id | uuid FK → test_runs.id, ON DELETE CASCADE | the run's uuid PK, not the varchar `test_run_id` |
| card_key | varchar(64) | stable card identifier; see Open Question 1 |
| parent_id | uuid FK → test_run_comments.id, ON DELETE CASCADE, nullable | non-null = reply; a reply's parent must be a root with the same run and card (service check) |
| body | text, CHECK `(deleted_at IS NULL AND length(body) BETWEEN 1 AND 10000) OR (deleted_at IS NOT NULL AND body = '')` | plain text, escaped on render (UI and report); wiped on soft delete |
| author_id | varchar(255) | Keycloak `sub`; API keys cannot write comments (403, eng review R3) |
| author_name | varchar(255) | snapshot at write time of `UserContext.displayName` (JWT `name` → `preferred_username` → email; eng review R2) |
| marker_seq | int, nullable | roots only; unique per run, never reused |
| marker_time | timestamptz, nullable | set iff `marker_seq` set (CHECK) |
| chart_context | jsonb, nullable | `{ series: MetricSeriesRef[], xRange: [iso, iso], presetId?: uuid }`; validated DTO, size-capped |
| organization_id / team_id | uuid | inherited from the run |
| created_at / updated_at / edited_at | timestamptz | `edited_at` drives "(edited)" |
| deleted_at | timestamptz, nullable | soft delete for marker roots and roots with replies (see Delete rule) |

Indexes: `(test_run_id, created_at)`, `(parent_id)` (the parent-side FK check is a scan per child without it, Common Issue #57), unique `(test_run_id, marker_seq) WHERE marker_seq IS NOT NULL`.

`marker_seq` assignment: `SELECT COALESCE(MAX(marker_seq),0)+1` inside the insert transaction, retry once on a unique violation. **A marker root is always soft-deleted, never hard-deleted**, whether or not it has replies, so its row keeps holding its number and MAX never goes down. Deleting ② leaves ③ as ③, and the next marker is ④.

**Delete rule (all comments).** A marker root, or any root with replies, is soft-deleted: `deleted_at` is set and `body` is wiped to `''` in the same UPDATE. A plain root without replies, and any reply, is hard-deleted. A soft-deleted comment returns `{ id, deleted: true, body: null, author_name, created_at }` from the API and the socket. The report shows "comment deleted" in its place, the channel post never counts or quotes it, and the SUT export carries the row with an empty body. A soft-deleted marker keeps its pin, rendered greyed out with its number. No new replies may be posted under a soft-deleted root (400).

`test_run_comment_reads`: PK `(user_id, test_run_id, card_key)`, `last_seen_at`, `organization_id`. **Reads are per card.** The run-header and test-run-list badges are the sum over cards. "Seen" means exactly one action: the drawer for that card is open. Opening the drawer upserts `last_seen_at = now()` for that card only, and so does a socket event arriving while the drawer is open. Loading the run page or expanding a card marks nothing.

Badge count for a card = comments on that run and card with `author_id <> me AND deleted_at IS NULL AND created_at > COALESCE(last_seen_at, '-infinity')`. Only comments from the last 30 days count (`COMMENT_UNREAD_WINDOW_DAYS`, eng review R7). **A missing reads row means every comment by others in that window is unread.** That does not flood the test-run list on day one, because runs from before the feature have no comments at all.

Both tables (and PR3's `notified_at` column and partial index) need migrations numbered above the current head (1826 at review time; never a SAVEPOINT, since every migration above 1791 runs after its bare COMMIT) (Common Issue #64), RLS policies, entity registration in shared (rebuild `packages/shared/dist`), and `check:entity-migrations` green. Decide SUT export inclusion (Open Question 4).

### API (new `comments` module in apps/api)

- `GET /test-runs/:id/comments?card=` (threads, roots plus replies), `POST /test-runs/:id/comments`, `PATCH /comments/:id` (author only; `body` only, eng review R5), `DELETE /comments/:id` (author, `OrganizationRole.ADMIN` in the comment's org, or global admin; eng review R13), `PUT /test-runs/:id/comments/seen` (body: required `card`), `GET /test-runs/:id/comments/unread` (per-card counts), and an unread count folded into the test-run list response.
- Every route resolves `accessibleOrgIds` once via `withOrgFilter` and passes it as a required parameter; out-of-scope returns 404; empty org list returns `[]` early.
- **Realtime.** Full `comment:created|updated|deleted` payloads go only to the per-run room `TestRunRooms.testRun(id)` (joined via the existing access-checked `subscribe:test-run`); org/team rooms get a body-free `comment:badge {testRunId, cardKey}` for list and card badges (eng review R12). Both are emitted through a new `emitCommentEvent(comment)` helper. The helper resolves rooms from the comment row's own `organizationId` / `teamId`, which were copied from the `test_runs` row at create, and **never from the caller's `UserCtx`**: `UserCtx.organizationId` is undefined for ordinary Keycloak logins (Common Issue #58), so a caller-derived room delivers nothing. It does not go through the TestRun mappers, and it must not rely on any fallback that lives only inside `emitTestRunEvent`. A comment without an organization is not emitted, and a WARN is logged; it is never broadcast. The payload for a deleted comment carries the redacted shape above.

### Notifications (PR3)

- Migration: `notification_channels.notify_on_comment boolean default false`; checkbox in the channel form.
- **Per-comment claim, no watermark.** `test_run_comments` gains `notified_at timestamptz NULL` (added in PR3's migration) and a partial index `(test_run_id) WHERE notified_at IS NULL AND deleted_at IS NULL`. Whether a comment has been announced is a property of the row, so commit order cannot cause a miss.
- **Sender: `@Cron` sweep in the API (eng review R1).** The API has no BullMQ worker, but it already runs `@Cron` jobs (`test-runs-stale-detection-scheduler.service.ts:22`). A `CommentNotificationScheduler` runs every 30 s:
  1. Find runs having comments with `notified_at IS NULL AND deleted_at IS NULL` whose oldest such comment has `created_at <= now() - 120 s` (served by the partial index).
  2. For each run, in one short transaction: take `pg_try_advisory_xact_lock` on a key derived from the run id (skip the run this tick if another replica holds it; eng review R15), then lock that run's unannounced, non-deleted comments with `SELECT … FOR UPDATE SKIP LOCKED`, `UPDATE … SET notified_at = now()`, and **commit before any webhook call** (eng review R4). `SKIP LOCKED` lets several API replicas run the sweep without double-posting.
  3. With no transaction open, post "N new comments on <SUT> run <id>", with the newest comment's author, card and a deep link built from `PERFANA_URL`, to every enabled channel of the SUT that has `notify_on_comment`. Each channel succeeds or fails on its own; a non-retryable failure (SSRF-guard refusal, 4xx, undecryptable URL, missing `ENCRYPTION_KEY`) is terminal for that channel and logged at ERROR naming the run and channel.
  4. If every channel failed and at least one failure was retryable (timeout, 5xx, network), release the batch: `UPDATE … SET notified_at = NULL WHERE id IN (<claimed ids>)`, so the next sweep retries it. Otherwise the claim stands.
- **Guarantee.** Every non-deleted comment is announced, in one post per burst, 120–150 s after the burst's first comment, except when the API crashes between the claim commit and the post: that batch is dropped (accepted, R4). Nothing is enqueued, so nothing can be swallowed. User edits never wait on a webhook. A soft-deleted comment is never claimed. When every channel fails non-retryably the claim is committed and the ERROR log names the broken channels.
- The three existing message builders gain a comment message. The existing SSRF guard and encryption apply unchanged.

### Web

- Run-header badge: a click jumps to the next card (page order) with unread comments, expands it and opens its drawer (eng review R6). Per-card badge via the page-level `<CardComments>` wrapper (D1); `CommentsDrawer` per card listing roots (marker threads and card threads), one expanded, reply box at the bottom; unread rows get the left rule and "new".
- Graphs card: "+ Add marker" toggle. A click on a plotted point snaps to that bucket: `marker_time = sortedTimestamps[pointIndex]`; pins render at the nearest visible bucket via the event-lines timestamp-to-index lookup, hidden when outside the plotted range (eng review R14). It also captures, as `chart_context`, the card's current series refs (capped at 50, the existing `LINK_WILDCARD_MAX_SERIES`), its x-range and its preset id, then opens a new thread. Markers render through the event-overlay path as numbered pins.
- **Marker view replay (new work, not the existing link path).** Today's `CardLinkRequest` (`page.tsx:235`) carries one `MetricSeriesRef` with no range and no preset, and the cascade only adds series. So PR2 adds a separate request on the same context: `GraphsViewRequest { key: 'comment:<id>', series: MetricSeriesRef[], xRange: [iso, iso], presetId?: string }`. `GraphsCard` consumes it once per `key`, using the same consumed-key guard as card links. It **replaces** the chart's series rather than merging into them, then applies the range through `applyZoomRange` so the data is refetched for that window. **The captured `series` are authoritative.** The preset, when `presetId` is set and still exists, contributes only display settings (`chartOptions.title` and `axisMode`; units stay per series). Its current series are ignored, so a preset edited after the marker was placed cannot change what the marker shows. It shows a "Previous view replaced · Undo" toast that restores the series and range the user had before. Refs that no longer resolve are skipped and counted in the drawer (Open Question 6). "Restore view" and the `?comment=` deep link both issue this request.
- `?card=&comment=` handling extends the existing `linkedCard` effect in `page.tsx`.
- All calls via `authenticatedFetch()`. Verify in a real browser with Vibium (memory: frontend changes).

### Reports (PR3)

- A new "Comments" report section type (eng review R8) (registered in both web and API registries), listing threads grouped by card, each marker thread headed by a server-rendered SVG chart from its `chart_context` with the numbered callout. All text HTML-escaped. See Open Question 2.

### PR2 as built (2026-11-20)

Four deliberate departures from the text above, each simpler and equivalent in effect:

- **`chart_context.series` is the graph-preset series shape** (`SeriesConfigDto`), not `MetricSeriesRef[]`. Replay is then the preset load path (`useGraphsData.loadView`), with no cascade walk. It still carries `dashboardLabel`/`panelId`/`metricName`, so R17's cross-run lookup keeps its key.
- **`title` and `axisMode` are captured instead of `presetId`.** The design used the preset for exactly those two display settings, and capturing them cannot drift when the preset is edited or deleted.
- **The `chart_context` byte cap is 64 KB, checked in `validateChartContext`, not 32 KB in the DTO** (R3-15). A view holds up to 50 series and a Trends series name may be 1024 characters, so 32 KB refused legitimate views; and since the request DTO types the view loosely (see below), the per-card check in the service is the only place that sees it whole.
- **`marker_seq` is serialized with `pg_advisory_xact_lock` per run, not retried on 23505.** A failed INSERT aborts the request's RLS transaction, so a retry would need a SAVEPOINT; the lock needs none. The unique index stays as the backstop.

One addition, asked for during review: **every root comment on Graphs, Trends and Compare records its card's view**, not only markers. `chart_context` carries a server-stamped `kind` and is validated per card in `validateChartContext` (the request DTO types it loosely, because one nested class would have the global whitelist strip the other cards' fields). Trends records its series, the time range option and the absolute window it resolved to (so "Last week" replays the week the author saw, as a custom range), and the aggregation; Compare records its series and baseline (a run id or `control-group`; a baseline no longer offered leaves the picker alone, as a preset does). An empty card records nothing, since the API refuses a view with no series. "Restore view" and the `?comment=` deep link replay any comment that has a view, through a card-tagged `viewRequest` each card consumes once per key, with an Undo.

Also fixed on the way: `CardComments` remounted its card when the panel opened, which dropped every card's local state (the Graphs chart emptied). Deferred items are in TODOS.md under "Test-run comments".

## Success Criteria

- Two users in two browsers: A places marker ② on a chart they built; B opens the deep link in a fresh session and sees the same series and range with ② on it.
- A reply appears for the other user within a second without reload (socket), and their card badge increments; opening the drawer clears it.
- A user from another organization gets 404 on every comment route for the run, including by comment id, and receives no socket events (RLS suite plus gateway spec).
- With `notify_on_comment` on, five comments posted within 120 s of the first unannounced one produce exactly one channel post with a working deep link.
- A report with the Comments section shows every thread with author and timestamp, and each marker as a numbered callout on its chart; an HTML payload in a comment body renders as text.

## Reviewer Concerns

### R3-1 — feasibility (blocking)

**Problem**

> Step 4 runs inside the processor, while the current job still exists under `comment-notify:<runUuid>`. BullMQ ignores an add whose jobId already exists, and `removeOnComplete` frees the id only after the processor returns. So step 4's re-enqueue is always swallowed: it is a no-op, not the catch-up the Guarantee relies on. The swallow window is also wider than the Guarantee says. Every comment that commits at any point while the job is active (after the step 1 claim, during the webhook posts and retries) has its own enqueue swallowed too, not only one that commits 'after step 4's check'. Such comments then wait, with no bound, until someone comments on that run again. In a morning-after review that may never happen.

**Remedy**

> Re-enqueue after the job id is released. For example, schedule from the worker's `completed`/`failed` event, or give each job a unique id (for example `comment-notify:<runUuid>:<claim timestamp>`) and use a separate pending marker for the sliding window, such as a Redis key with a TTL or BullMQ's deduplication option. Then restate the Guarantee to match the mechanism you chose.

### R3-2 — feasibility (blocking)

**Problem**

> A channel that fails permanently blocks the claim for every channel, for good. Causes include an SSRF-guard refusal, a 4xx from a revoked webhook, an undecryptable URL, or a missing ENCRYPTION_KEY, and each one fails on every attempt. Each job then posts to the healthy channels up to 3 times (once per attempt), rolls back, and leaves the comments unclaimed. The next comment's job reposts them all again, with a larger N. The design accepts a duplicate only 'after a partial failure'. Here the duplication repeats without end and grows, and nothing is ever marked announced.

**Remedy**

> Track delivery per channel. Option 1: a per-(comment batch, channel) delivery record. Option 2: commit the claim once at least one channel succeeds, and log the failed channels at ERROR. Either way, treat non-retryable failures (guard refusal, 4xx, decryption failure) as terminal for that channel rather than a reason to retry the whole job.

### R3-3 — feasibility (blocking)

**Problem**

> Step 1 claims only rows with `deleted_at IS NULL`, but step 4's check and the partial index `(test_run_id) WHERE notified_at IS NULL` do not exclude soft-deleted rows. A soft-deleted marker root, or a root with replies deleted before any job claimed it, keeps `notified_at IS NULL` forever. Once step 4 works (R3-1), every job on that run finds it 'unclaimed', claims nothing, posts nothing and re-enqueues. The result is an endless 120 s job loop per affected run.

**Remedy**

> Use step 1's predicate in step 4 (`notified_at IS NULL AND deleted_at IS NULL`), and put the same predicate in the partial index. Alternatively, set `notified_at` when a comment is soft-deleted.

### R3-4 — feasibility (minor)

**Problem**

> The claim holds a database transaction, and row locks on every claimed comment, across sequential webhook calls. Each call can wait up to DELIVERY_TIMEOUT_MS (webhook-target-guard.ts), times the number of channels. Meanwhile a user's PATCH or DELETE on any of those comments blocks, along with its request's RLS transaction and pooled connection.

**Remedy**

> Do not post while the claim's transaction is open. Option 1: claim and commit with a status such as 'sending', then post. Option 2: take the claim with a short `lock_timeout`, and have PATCH/DELETE use `NOWAIT`/`SKIP LOCKED` semantics. State which one.

### R3-5 — completeness (minor)

**Problem**

> Carried from R2-5, partly resolved because the third table is gone. The API-side processor has no request context, yet it UPDATEs `test_run_comments`, an RLS table. The design does not say which role or context it runs under (perfana_system, a bypass login, or system-call GUCs).

**Remedy**

> State the database role or context the processor's claim and SELECTs use, and confirm the RLS policies allow it.

**Remedy**

### Unresolved at the cap

1. R3-1 — feasibility (blocking): Step 4 runs inside the processor, while the current job still exists under `comment-notify:<runUuid>`. BullMQ ignores an add whose jobId already exists, and `removeOnComplete` frees the id only after the processor returns. So step 4's re-enqueue is always swallowed: it is a no-op, not the catch-up the Guarantee relies on. The swallow window is also wider than the Guarantee says. Every comment that commits at any point while the job is active (after the step 1 claim, during the webhook posts and retries) has its own enqueue swallowed too, not only one that commits 'after step 4's check'. Such comments then wait, with no bound, until someone comments on that run again. In a morning-after review that may never happen.
2. R3-2 — feasibility (blocking): A channel that fails permanently blocks the claim for every channel, for good. Causes include an SSRF-guard refusal, a 4xx from a revoked webhook, an undecryptable URL, or a missing ENCRYPTION_KEY, and each one fails on every attempt. Each job then posts to the healthy channels up to 3 times (once per attempt), rolls back, and leaves the comments unclaimed. The next comment's job reposts them all again, with a larger N. The design accepts a duplicate only 'after a partial failure'. Here the duplication repeats without end and grows, and nothing is ever marked announced.
3. R3-3 — feasibility (blocking): Step 1 claims only rows with `deleted_at IS NULL`, but step 4's check and the partial index `(test_run_id) WHERE notified_at IS NULL` do not exclude soft-deleted rows. A soft-deleted marker root, or a root with replies deleted before any job claimed it, keeps `notified_at IS NULL` forever. Once step 4 works (R3-1), every job on that run finds it 'unclaimed', claims nothing, posts nothing and re-enqueues. The result is an endless 120 s job loop per affected run.

### Design decisions
- **DR1 (Pass 1, answer A):** each expanded thread ends with its own reply box; a "New comment on this card" composer is pinned at the top of the drawer (on the Graphs card it sits beside "+ Add marker"). No shared bottom reply box.
- **DR2 (Pass 1, answer A):** card badge states: unread > 0 → filled count pill; comments but none unread → small outlined comment icon, no number; no comments → outlined icon appears only on card hover or keyboard focus. Never a "0" pill.
- **DR3 (Pass 1, answer A):** drawer list order: threads with unread replies first, then by latest activity. Each collapsed row: pin (②) or comment icon · root author · one-line root excerpt · reply count · latest-activity time. The oldest unread thread auto-expands on open.

- **DR4 (Pass 2, answer A):** when a drawer opens, the client snapshots the previous `last_seen_at` for that card; threads newer than it keep the "new" mark until the drawer closes or the card changes, while the server is told "seen" immediately and the badge clears at once.

- **DR5 (Pass 2, answer A):** marker placement flow: with "+ Add marker" on, crosshair cursor and a faint dashed preview line snapping to the nearest bucket on hover; click → pending unnumbered pin + composer focused with placeholder "Describe what happens at <time>…"; posting assigns the next `marker_seq`; Esc, Cancel or closing the drawer removes the pending pin; the mode switches off after one marker.

- **DR6 (Pass 2, answer A):** interaction state table adopted:

```

               | locked             | 9,000 of 10,000                        |                                          |
Edit           | Save spinner       | —                                      | text kept, inline "Not saved · Retry"    | "(edited)" appears
Delete         | —                  | —                                      | toast "Couldn't delete"                  | confirm "Delete this comment?"; then "Comment deleted" placeholder (soft) or row removed (hard)
Marker replay  | chart skeleton     | —                                      | "Marker view unavailable" + thread opens | partial: "1 of 3 series no longer available"
Marker pin     | —                  | —                                      | —                                        | outside range: drawer chip "Outside current view · Show"; same bucket: pins stack ②③
```
